`ticket_ref.workspace` in list/get HTTP responses echoes a workspace id that does not match the requested (and valid) `workspace` query parameter, and does not correspond to any workspace registered in `WorkspaceRegistry`. The frontend trust point (`TicketSummary::resolved_ticket_ref`) uses the echoed value to build follow-up `?view=full` requests, which then 404 because the workspace id is unregistered. Root cause is a divergence between `owning_workspace_for_path` (label/scan-root matching) and `canonical_workspace_name_for_index_root`/`short_workspace_hash` (canonical hashed id) — these two computations must be unified so `ticket_ref.workspace` always equals a workspace id present in `GET /workspaces`.
