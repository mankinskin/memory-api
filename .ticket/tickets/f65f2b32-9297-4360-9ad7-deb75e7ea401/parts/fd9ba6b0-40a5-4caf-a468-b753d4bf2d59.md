Pre-existing defect discovered (NOT caused by this migration/rendering work, does not regress anything the migration touched): the ticket list/search API response's `ticket_ref.workspace` field is, for most tickets in the repo (all tested except the freshly-migrated e342cc4c), a mismatched workspace hash that is never registered in `WorkspaceRegistry` (e.g. requesting ticket 3a1ec9f8 with the valid, registered `workspace=memory-api--a6b09287` still returns `ticket_ref.workspace: "memory-api--8c1a6067"` in the payload; requesting `?view=full` with either the requested or the echoed hash then 404s with `workspace not found`). The frontend's `TicketSummary`/`TicketDetail::resolved_ticket_ref` (memory-viewers/ticket-viewer/frontend/dioxus/src/types.rs:92-104, :293-306) unconditionally trusts this echoed `ticket_ref.workspace` over the workspace actually being browsed, so clicking almost any ticket in the list opens the detail pane with the wrong workspace and the `Document` tab shows a `desc-error` banner (`workspace not found`) instead of the typed-parts panel — no blank page, no crash, but the parts view cannot be confirmed by normal UI navigation for these tickets. Root cause looks backend-side (registry/index workspace-name computation divergence between the registered `WorkspaceRegistry` primary name and whatever value gets attached to a ticket row's `ticket_ref` at index time); not a trivial frontend fix, out of scope for this verification pass. Worked around for scenarios (a) using the one unaffected ticket; scenarios (b)-(e) verified only at the API layer (`GET /api/tickets/{id}?view=full`, confirmed correct part/ref shape for all four) plus DOM confirmation that the document shell itself never renders blank.
