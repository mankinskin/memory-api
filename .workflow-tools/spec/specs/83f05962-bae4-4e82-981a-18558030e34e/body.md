# PDF Domain Tooling

## Purpose

Give agents a first-class, safe way to work with PDF files: extract text and
images, edit and merge documents, and create new ones. Delivered as a Rust
domain crate exposed over MCP, plus a skill that makes the capability
discoverable.

## Requirements

### R1 — Capability surface

The domain must support:

1. Extract text from a PDF, with page selection and bounded output.
2. Merge N PDFs into one, preserving input order.
3. Split one PDF into per-page or per-range documents.
4. Edit pages: delete, reorder, rotate.
5. Read and write document metadata.
6. Create a new PDF.
7. Extract embedded raster images (lowest priority; may be cut).

### R2 — Crate structure

The domain follows `WORKFLOW_TOOLS_DOMAIN_CRATE_CONTRACT.md`: an internal
`pdf-api` crate holding all types, logic, and errors, and a public facade crate
`pdf` that re-exports it and owns feature-gated transport binaries named exactly
`pdf-cli` and `pdf-mcp`. Both crates live under `memory-api/crates/` and are
registered in the root workspace.

This is a deliberate choice of the written contract over the prevailing
three-separate-crates precedent used by `peek`, `ticket`, `spec`, and others.
`memory-api/crates/ticket` already implements the contract shape and is the
reference.

### R3 — Pure-Rust dependency constraint

The implementation must be pure Rust. No C/C++ bindings, no `*-sys` crates, no
bundled native binaries — not even behind an optional feature. This preserves
reproducible builds and cross-platform CI without a native toolchain.

Consequence: any capability that has no viable pure-Rust implementation is cut,
not worked around by relaxing this constraint.

### R4 — Write safety

Copy-on-write is the default. Every write operation requires an explicit output
path; no output path is ever derived implicitly from an input path. Overwriting
an existing file requires an explicit `overwrite: true` in the request.
In-place modification writes to a temporary file and renames, so a failure
cannot destroy the source document.

Multi-output operations (split, image extraction) validate every destination
before writing any of them, so a rejection cannot leave a partial output set.

### R5 — Sandboxing

Every input and output path is confined to an allowlisted root, with no opt-out.
Confinement reuses `fs-api::security::validate_path_within_root`, which
canonicalizes both path and root to defeat symlink and Windows-junction escapes
and handles not-yet-existing destinations by canonicalizing the parent.

For the MCP transport, the root is configured at server startup and supplied by
the server, not the caller. A caller-supplied root that could widen the
boundary defeats the control and is not permitted.

### R6 — External tool policy

PDF creation offers a programmatic primitive that is always available, plus an
optional path that invokes `typst-cli` as an external process when it is
present on PATH. `typst-cli` is not a build dependency. When it is absent the
API returns a distinct, actionable error; it never panics and never silently
falls back to the programmatic mode, since a silent downgrade would produce a
document unlike what was requested.

External process invocation must not go through a shell, must not allow
caller input to inject additional CLI flags, must constrain the external tool's
own file access to the sandbox root, and must apply a wall-clock timeout and
output size cap.

### R7 — Output bounding

Bounding lives in `pdf-api`, not in the transports, matching the `peek-api`
convention. Text extraction has a documented default character cap and a
truncation indicator so a caller knows output was cut and can narrow the
request. Transports must not remove or bypass bounding.

### R8 — Error classification

`PdfError` distinguishes user errors from internal errors via a predicate, so
the MCP transport maps them to `invalid_params` and `internal_error`
respectively, and the CLI maps them to distinct exit codes.

### R9 — Agent discoverability

A hand-authored skill at `.agents/skills/pdf/SKILL.md` documents the capability.
It is not generated by the rule system and carries no generated-file header. Its
`description` frontmatter must state concrete trigger conditions, because skills
load by description. It directs agents to the `pdf-mcp` named tools and
documents `pdf-cli` as the fallback.

### R10 — Known limitations to document

- Scanned/image-only PDFs have no text layer. Extraction must signal this
  explicitly rather than returning a bare empty result. OCR is out of scope.
- Image extraction may not support exotic filters or colorspaces; unsupported
  images are skipped and reported, never emitted corrupt. CCITTFaxDecode (G3/G4
  fax) and JPXDecode (JPEG 2000) are the expected gaps and are named explicitly
  in the agent-facing documentation.
- typst-based creation is unavailable without `typst-cli`.
- Password-protected PDFs are rejected with a distinct, actionable error rather
  than a generic parse failure. PDFs encrypted with an empty user password
  (permission-locked but not password-protected) are processed transparently,
  because the underlying crate handles them without our involvement.
- Structurally malformed or non-conformant PDFs are not repaired; they surface
  as a normal error.

## Non-Goals

- HTTP transport in v1 (deferred, tracked separately).
- Native/C++ bindings.
- Viewer or frontend crate.
- OCR.
- Form filling, digital signatures, encryption. Accepting a password, decrypting,
  or encrypting output are all out of scope; only error classification for
  encrypted inputs is in scope.
- Repair or recovery of malformed / non-conformant PDF structure.
- PDF/A archival conformance.

## Open Risk

This spec was originally authored without web access, leaving every crate fact
unverified. A dedicated research pass has since confirmed versions, licences,
maintenance status, and pure-Rust status for the candidate set, and has resolved
the merge object-ID renumbering approach and the typst CLI contract. `krilla` is
the selected creation backend; `printpdf` is dropped.

T0 round 1 (empirical verification spike, scratch crate at
`target/tmp/pdf-spike/`) has since resolved most of what remained open:

- **CCITTFax/JPX image filter risk — RESOLVED.** Confirmed by reading `lopdf`
  0.44.0 source (`src/object.rs`) that its stream decoder implements only
  `FlateDecode`, `LZWDecode`, and `ASCII85Decode`: CCITTFaxDecode and JPXDecode
  are confirmed absent from `lopdf`'s own decoding. However,
  `Document::get_page_images` returns the raw encoded stream bytes plus the
  filter list regardless of filter, so DCTDecode (JPEG) and JPXDecode
  (JPEG2000) streams remain extractable as passthrough — the raw bytes are
  themselves a complete, directly openable file. CCITTFax has no usable
  container without a dedicated decoder `lopdf` does not have, and is treated
  as unsupported/skip-with-reason per R10.
- **krilla font asset risk — RESOLVED.** Confirmed by reading and exercising
  krilla 0.8.2's public API that every text-drawing call requires an explicit
  `Font`; `Font` has no `Default` impl and no no-embed text path exists. Font
  bytes are a hard requirement, not a contingency. `NotoSans-Regular.ttf`
  (OFL-licensed, vendored by krilla itself as a test/example asset) is the
  named candidate; final selection and provenance recording remains T5's.
- **pdf-extract failure modes — PARTIALLY resolved.** The missing-`MediaBox`
  panic was empirically triggered (`pdf-extract` panics at `src/lib.rs:2408`
  with payload `"MediaBox"`) and `catch_unwind(AssertUnwindSafe(...))` was
  confirmed to contain it, validating the planned panic-containment design.
  Missing-ToUnicode CMap, unusual Type0/CID encodings, scanned/no-text-layer
  pages, and malformed-xref behavior were **not** exercised in round 1 and
  remain open pending a second verification-spike round.

The verification spike still gates all dependency selection. The remaining
open item — full `pdf-extract` failure-mode coverage beyond the MediaBox
case — is scoped to a second T0 round rather than assumed complete; the
possibility that image extraction is cut under R3 no longer applies now that
DCT/JPX passthrough is confirmed viable.

**Decision (2026-07-28): this spec's `draft` state does not gate ticket
`fc94716e` (T0) moving to `in-review`.** The spec remains in `draft` while T0's
verification-spike findings above are incorporated; ticket state transitions
for T0 are the orchestrator's decision and are not blocked on this spec's
lifecycle state.
