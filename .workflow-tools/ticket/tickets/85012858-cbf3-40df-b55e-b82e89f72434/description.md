## Research Brief (2026-08-06)

1. **Current schema model**

   Ticket schemas are `TicketTypeSchema` aliases of the shared `memory_api::model::schema::EntityTypeSchema` model; the shared model stores `type_id`, field definitions, a flat `Vec<String>` of state names, `Vec<Transition>`, relation `edge_rules`, required states, and terminal states at [memory-api/crates/memory-api/src/model/schema.rs](memory-api/crates/memory-api/src/model/schema.rs#L35-L56). `Transition` carries only `from` and `to` strings at [memory-api/crates/memory-api/src/model/schema.rs](memory-api/crates/memory-api/src/model/schema.rs#L35-L39). No parent identifier, resolved node type, category label, source hash, manifest, or cache field exists in `EntityTypeSchema`; the flat field list is the direct proof that no inheritance mechanism exists today at [memory-api/crates/memory-api/src/model/schema.rs](memory-api/crates/memory-api/src/model/schema.rs#L42-L56). The governing contract instead requires strict runtime single-parent inheritance, cached dynamic resolution, and `plan`/`act`/`verify` node categories in [transcripts/05-08-2026_ticketschema-state-machines/interview.md](transcripts/05-08-2026_ticketschema-state-machines/interview.md#L13-L31) and [transcripts/05-08-2026_ticketschema-state-machines/interview.md](transcripts/05-08-2026_ticketschema-state-machines/interview.md#L191-L233).

2. **Current registry / load path**

   `ticket_api::model::schema_registry::SchemaRegistry` owns only `BTreeMap<String, TicketTypeSchema>` at [memory-api/crates/ticket-api/src/model/schema_registry.rs](memory-api/crates/ticket-api/src/model/schema_registry.rs#L12-L20). `with_builtins` parses embedded ticket TOML through `builtin_schemas` and inserts each result at [memory-api/crates/ticket-api/src/model/schema_registry.rs](memory-api/crates/ticket-api/src/model/schema_registry.rs#L23-L34); built-ins are explicitly embedded TOML sources at [memory-api/crates/ticket-api/src/model/default_schema.rs](memory-api/crates/ticket-api/src/model/default_schema.rs#L3-L39). `load_dir` walks `*.toml` entries and calls `load_file`, while `load_file` reads, TOML-deserializes, and immediately inserts/replaces the live map entry at [memory-api/crates/ticket-api/src/model/schema_registry.rs](memory-api/crates/ticket-api/src/model/schema_registry.rs#L36-L67).

   Load is **not atomic today**: a later `load_file` failure occurs after any earlier insertion in the same `load_dir` loop at [memory-api/crates/ticket-api/src/model/schema_registry.rs](memory-api/crates/ticket-api/src/model/schema_registry.rs#L40-L50). No generation concept exists: the registry has only the `schemas` map and exposes direct lookup/type-ID iteration at [memory-api/crates/ticket-api/src/model/schema_registry.rs](memory-api/crates/ticket-api/src/model/schema_registry.rs#L17-L20) and [memory-api/crates/ticket-api/src/model/schema_registry.rs](memory-api/crates/ticket-api/src/model/schema_registry.rs#L70-L81). No resolved-schema cache exists: neither the registry field set nor the loading path has cache/hash/manifest state at [memory-api/crates/ticket-api/src/model/schema_registry.rs](memory-api/crates/ticket-api/src/model/schema_registry.rs#L17-L67). Track 1 therefore needs a build-then-swap registry generation so parent/cycle/type-ID failure retains the prior valid generation and atomically couples source/ancestor-hash invalidation with the resolved cache, manifest/catalog, and client cache version, as required by [transcripts/05-08-2026_ticketschema-state-machines/interview.md](transcripts/05-08-2026_ticketschema-state-machines/interview.md#L278-L305).

3. **Current transition validation**

   `TicketStore::resolve_transition_path` loads the type schema, calls `schema.find_path` for every supplied checkpoint/target, auto-walks reachable intermediates unless `single_hop` is requested, and rejects an unreachable target through `invalid_transition_error` at [memory-api/crates/ticket-api/src/storage/store.rs](memory-api/crates/ticket-api/src/storage/store.rs#L849-L927). The shared schema model is graph-shaped rather than a flat allowed-target set because it stores `Transition { from, to }` edges at [memory-api/crates/memory-api/src/model/schema.rs](memory-api/crates/memory-api/src/model/schema.rs#L35-L46). Current validation is nevertheless **undirected**: `allows_transition` accepts either orientation, and `allowed_next_states` reports adjacency in both orientations at [memory-api/crates/memory-api/src/model/schema.rs](memory-api/crates/memory-api/src/model/schema.rs#L77-L105). No lifecycle-category concept exists in the model fields at [memory-api/crates/memory-api/src/model/schema.rs](memory-api/crates/memory-api/src/model/schema.rs#L42-L56). The planner must replace the undirected interpretation with a directed resolved lifecycle graph that permits only category-contained edges, neighbouring-category edges, defined rework/replan edges, and the cancellation exception from the interview contract at [transcripts/05-08-2026_ticketschema-state-machines/interview.md](transcripts/05-08-2026_ticketschema-state-machines/interview.md#L201-L251).

4. **Lifecycle vs relation graph separation**

   Edge mutation is separately implemented by `TicketStore::add_edge`: it validates endpoint visibility, consults a source schema's `edge_rules` for acyclicity, writes the file-backed relation, inserts the query index edge, and refreshes facts for changed `depends_on` edges at [memory-api/crates/ticket-api/src/storage/store/query.rs](memory-api/crates/ticket-api/src/storage/store/query.rs#L136-L201). However, `resolve_transition_path` calls `TicketStore::enforce_dependency_progress` before resolving lifecycle reachability at [memory-api/crates/ticket-api/src/storage/store.rs](memory-api/crates/ticket-api/src/storage/store.rs#L849-L880). `enforce_dependency_progress` then iterates `edges_from`, filters `depends_on`, ranks target/dependency states, and rejects the transition when target progress exceeds the dependency's rank at [memory-api/crates/ticket-api/src/storage/store.rs](memory-api/crates/ticket-api/src/storage/store.rs#L930-L977).

   This is the compatibility-critical entanglement: lifecycle resolution directly invokes relation-progress validation, despite the interview defining state transitions as the lifecycle graph and ticket links as a relation graph with no lifecycle-category constraints at [transcripts/05-08-2026_ticketschema-state-machines/interview.md](transcripts/05-08-2026_ticketschema-state-machines/interview.md#L252-L276). The planner should remove dependency-progress checking from lifecycle path resolution and retain it as a separately invoked relation/workflow policy gate, preserving the existing dependency-order business rule without assigning relation edges lifecycle categories.

5. **Spec and rule store parallels**

   The spec store parses embedded `specification.toml` into the shared `EntityTypeSchema` and registers it in the shared `memory_api::model::schema_registry::SchemaRegistry` at [memory-api/crates/spec-api/src/default_schema.rs](memory-api/crates/spec-api/src/default_schema.rs#L1-L24). The rule store does the same for `rule-entry.toml` and `generated-target.toml` at [memory-api/crates/rule-api/src/default_schema.rs](memory-api/crates/rule-api/src/default_schema.rs#L1-L25). The stores already share the generic schema model/registry crate but duplicate local embedded-source parsing and local registry construction; the interview requires shared directed primitives while preserving separate local graphs and type-ID namespaces at [transcripts/05-08-2026_ticketschema-state-machines/interview.md](transcripts/05-08-2026_ticketschema-state-machines/interview.md#L23-L31). Track 1 can therefore centralize resolved directed primitives and registry mechanics, while leaving ticket/spec/rule source discovery, graph instances, and namespace validation local.
