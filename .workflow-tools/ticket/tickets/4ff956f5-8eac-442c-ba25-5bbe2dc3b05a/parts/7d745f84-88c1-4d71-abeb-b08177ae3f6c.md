## Objective

Implement page/document-level operations: merge multiple PDFs into one, split a PDF into per-page (or per-range) output files, reorder/delete pages within a PDF, and read/write document metadata (title, author, subject, keywords, etc.).

## Target Files

- `memory-api/crates/pdf-api/src/lib.rs` (or `src/pages.rs`, `src/metadata.rs` if split out) — implement `Merge`, `Split`, `ReorderPages`, `DeletePages`, `ReadMetadata`, `WriteMetadata` request variant bodies.
- `memory-api/crates/pdf-api/tests/` — tests for each operation using small multi-page fixture PDFs.

## Design

Implement using the crate T0 selected for structural PDF editing (candidate: `lopdf`, to be confirmed by T0). All operations route through the T2 sandboxing + write-safety layer already in place — no new path-validation logic here.

- **Merge**: takes an ordered list of input PDF paths, produces one output PDF containing all pages in input order. Reject empty input list as a user error.
- **Split**: takes one input PDF and an output directory, produces one output file per page (or per contiguous range if the request shape from T2 supports ranges — confirm against the finalized `PdfRequest::Split` shape). Naming convention for split output files must be deterministic (e.g. `<original-stem>-page-<n>.pdf`), documented here once implemented.
- **ReorderPages / DeletePages**: takes an input path, an explicit `output` path, and a page index list; page indices are 0-based (or 1-based — pick one and document it consistently across the whole crate, including in the skill doc from T8). Out-of-range page indices are a user error, not a panic.
- **ReadMetadata**: returns whatever standard metadata fields the input PDF has set (title, author, subject, keywords, creator, producer, creation/mod dates) as an optional-field struct — absent fields are `None`, not empty-string.
- **WriteMetadata**: takes an input path, explicit `output` path, and a metadata struct with optional fields; only overwrites the fields provided (fields left `None` in the request preserve the existing value from the input document).

All output-producing operations enforce the copy-on-write / `overwrite` flag semantics from T2.

## Acceptance Criteria

- [ ] `Merge` combines N input PDFs into one output file with total page count equal to the sum of input page counts, in input order.
- [ ] `Merge` rejects an empty input list as a user error.
- [ ] `Split` produces one output file per page (or per range) with a documented, deterministic naming scheme.
- [ ] `ReorderPages` produces an output PDF with pages in the requested order; an out-of-range page index is rejected as a user error, not a panic.
- [ ] `DeletePages` produces an output PDF missing exactly the requested pages, with remaining pages preserved in original relative order.
- [ ] `ReadMetadata` returns `None` for unset fields and the correct value for fields that are set on a fixture PDF with known metadata.
- [ ] `WriteMetadata` updates only the fields provided in the request and preserves all other existing metadata and page content unchanged.
- [ ] All output-producing operations in this ticket refuse to overwrite an existing output path unless `overwrite: true` (reusing, not reimplementing, T2's enforcement).
- [ ] `cargo test -p pdf-api` passes including new tests for merge, split, reorder, delete, read-metadata, write-metadata.
