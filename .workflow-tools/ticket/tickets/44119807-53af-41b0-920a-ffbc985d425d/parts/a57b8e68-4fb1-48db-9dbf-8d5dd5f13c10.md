1. **`build_tool_response_override`** ([copilot-capture-hook.rs](memory-api/crates/session-api/src/bin/copilot-capture-hook.rs#L112-L142)): bare/suffixed split via `tool_use_id.split("__vscode-").next()` is sound for the observed VS Code convention and matches the transcript's bare `toolCallId`. 2. **`stat_spill_output_chars`** ([copilot-capture-hook.rs](memory-api/crates/session-api/src/bin/copilot-capture-hook.rs#L152-L177)): correctly derives `chat-session-resources/<session_id>/<tool_use_id>` from `transcript_path.parent().parent()`, matching the real `GitHub.copilot-chat/transcripts/<session>.jsonl` → `GitHub.copilot-chat/` sibling layout. Retries 5×100ms (~400ms worst case) before giving up; returns `None` (never a fabricated 0) on failure. Sound.
3. **`apply_tool_response_override`** ([transcript.rs](memory-api/crates/session-api/src/hook/transcript.rs#L253-L282)): correctly matches only terminal events by bare `tool_call_id`, overwrites both `output_chars` and `output_source` together, and `break`s after the first match (single-apply, no risk of double-application across duplicate terminal events for the same call).
4. **Retry loop in `capture_copilot_transcript_with_tool_response`** ([capture_query.rs](memory-api/crates/session-api/src/store/config/capture_query.rs#L59-L96)): confirmed the retry loop is gated behind `if let Some(override_value) = &tool_response_override` — it does **not** run at all when `build_tool_response_override` returns `None` (i.e., no `tool_use_id`, or output_chars couldn't be resolved from either hook-payload or spill file). This is a correct, bounded loop: `MAX_ATTEMPTS = 12`, `RETRY_DELAY = 200ms`, and the loop breaks immediately once `override_applied` returns true. No risk of an infinite loop — the attempt counter is a fixed range, and the final iteration (`attempt == 11`) breaks without sleeping. Minor precision note: worst-case sleep total is **11 × 200ms = 2.2s**, not literally "12 × 200ms = 2.4s" as the ticket description states (the 12th attempt is a poll with no trailing sleep) — a cosmetic overstatement, not a functional issue.
5. **Compounding latency the ticket description does not fully surface**: `stat_spill_output_chars`'s own internal retry (up to ~400ms) runs *before* `build_tool_response_override` can return `Some`, and it runs whenever the hook payload's `tool_response` is empty (documented as the common case for tools like `read_file`) — **regardless of whether the spill file ever appears**, i.e. even for calls that ultimately produce no override at all and thus never engage the 2.2s transcript-retry loop. So the ticket's framing ("added latency ... only when an override candidate exists") is only exactly true for the 2.2s transcript-retry stage; a *separate* ~400ms stage can be paid on tool calls that never resolve an override candidate at all. Worst-case combined added latency per hook invocation, when both stages are engaged and both eventually succeed, is closer to **~2.6s**, not ~2.4s.
