## Objective

Build the `pdf-api` core: a tagged request/response type system covering all six v1 operations, a `thiserror` error enum, a single `execute()` dispatch function, and the shared write-safety + sandboxing enforcement layer used by every operation.

## Target Files

- `memory-api/crates/pdf-api/src/lib.rs` (or split into `src/request.rs`, `src/response.rs`, `src/error.rs`, `src/security.rs`, `src/execute.rs` mirroring `fs-api`'s module split)
- `memory-api/crates/pdf-api/Cargo.toml` (add PDF-processing dependencies selected by T0's findings, plus `serde`, `serde_json`, `thiserror`)

## Design

Follow the `peek-api` shape (`memory-api/crates/peek-api/src/lib.rs`): a single tagged serde request enum, e.g.

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "kind")]
pub enum PdfRequest {
    ExtractText { path: PathBuf },
    ExtractImages { path: PathBuf, output_dir: PathBuf },
    Merge { inputs: Vec<PathBuf>, output: PathBuf, overwrite: bool },
    Split { path: PathBuf, output_dir: PathBuf },
    ReorderPages { path: PathBuf, output: PathBuf, order: Vec<usize>, overwrite: bool },
    DeletePages { path: PathBuf, output: PathBuf, pages: Vec<usize>, overwrite: bool },
    ReadMetadata { path: PathBuf },
    WriteMetadata { path: PathBuf, output: PathBuf, metadata: PdfMetadata, overwrite: bool },
    CreateProgrammatic { output: PathBuf, spec: PdfCreateSpec, overwrite: bool },
    CreateFromTypst { source: PathBuf, output: PathBuf, overwrite: bool },
}
```
(Field names/shape are illustrative; finalize field names to match whatever the T0-selected crates naturally expose, but the tagged-enum-of-operations structure itself is fixed by this ticket.)

A single dispatch function:
```rust
pub fn execute(root: &Path, request: &PdfRequest) -> Result<PdfResponse, PdfError>
```
`root` is the allowlisted confinement root (mirrors `fs-api`'s `root` parameter pattern in `mutation.rs`).

**Sandboxing**: every path in every request variant (input and output) must be validated with a `pdf-api`-local port of `validate_path_within_root` from `memory-api/crates/fs-api/src/security.rs` (either by depending on `fs-api` directly and reusing its function, or by copying the canonicalize-then-prefix-check logic into a local `pdf-api::security` module — prefer depending on `fs-api` directly if that does not create a circular/undesirable dependency; document whichever choice is made in this ticket's implementation).

**Write safety**: any operation that produces an output file must:
- Require an explicit `output` path in the request (no defaulting to overwriting the input).
- Reject the operation with a `PdfError` variant (e.g. `PdfError::OutputExists`) if `output` already exists and the request's `overwrite` field is not `true`.
- Only overwrite when `overwrite: true` is explicitly set.

`PdfError` (thiserror) must have distinct variants for: path escapes root, output exists without `overwrite`, input file not found, malformed/corrupt PDF, unsupported operation, and an underlying-crate error passthrough variant. Map errors to MCP `invalid_params` (user error: bad path, missing overwrite flag, bad page index) vs `internal_error` (corrupt PDF, unexpected crate failure) — the exact mapping ships in T7, but `PdfError` variants must be classifiable as user-error vs internal-error at that layer.

Do not implement PDF-format-specific logic bodies for text extraction, image extraction, merge/split, metadata, or creation in this ticket — those are stubbed (e.g. `todo!()` or minimal pass-through) and filled in by T3/T4/T5/T9. This ticket's scope is the request/response/error/dispatch/security skeleton, not full operation bodies. (If the T0-selected crates make a given operation trivial to implement immediately, doing so here is acceptable but not required.)

## Acceptance Criteria

- [ ] A single tagged serde request enum exists covering all six v1 capabilities (text extraction, image extraction, merge, split, page reorder/delete, metadata read+write, creation programmatic, creation via typst).
- [ ] A single `execute(root, request) -> Result<PdfResponse, PdfError>` dispatch function exists and routes every request variant.
- [ ] Every request variant containing a filesystem path is validated against `root` before any file I/O occurs, rejecting paths that escape the root (unit test proves a `../` or symlink-escape path is rejected).
- [ ] Any request variant that writes an output file returns `PdfError` when the output path exists and `overwrite` is not `true` (unit test proves this).
- [ ] The same request variant succeeds and overwrites when `overwrite: true` is set and the output already exists (unit test proves this).
- [ ] `PdfError` is a `thiserror`-derived enum with distinct variants distinguishing user error from internal error.
- [ ] `cargo build -p pdf-api` succeeds with the T0-selected PDF-processing dependencies added to `Cargo.toml`.
- [ ] `cargo test -p pdf-api` passes.
